# muse-ai-local-bridge — Protocol Specification (V1)

This document is the **shared syntax** of the project: the precise wire
format between the bridge server (running on the user's machine) and any
client (e.g. Muse at muse.ai). It is written so that anyone can
reimplement either side without reading the server source code.

Normative keywords (MUST, MUST NOT, SHOULD) are used in the RFC 2119 sense.

## 0. Design rationale (read this before "cleaning up" the protocol)

The protocol is **GET-based tool API**, not standard MCP Streamable HTTP.
This is deliberate, not legacy:

- The primary client (Muse at muse.ai) runs in a sandbox whose egress
  proxy **blocks outbound HTTP POST**. MCP Streamable HTTP is POST-only
  client → server, so a pure-MCP bridge would be unreachable from the
  chat it is built for.
- Standard MCP remains on the roadmap for universal clients, but V1
  speaks this GET protocol. Do not "upgrade" it without solving the
  POST-egress constraint first.

## 1. Transport

- Base URL: the public tunnel URL chosen by the user, e.g.
  `https://xxx.trycloudflare.com`. The server itself listens on
  localhost only; the tunnel is the sole ingress.
- All requests are HTTP GET. There is no request body.
- All endpoints require authentication (Section 2), no exceptions.
- **Practical payload limit:** tool arguments travel in the URL query
  string, so very large calls can be dropped by intermediaries. Observed
  in practice: a 22 KB `write_file` call had its connection closed without
  response, while a 7.3 KB call succeeded. Clients SHOULD keep a single call
  under ~7 KB and split large writes into sequential chunks (e.g.
  `write_file` the first chunk, then `edit_file` appends). Servers MUST NOT
  silently truncate arguments — oversized input should fail loudly.

## 2. Authentication

- The client MUST send the token in the `X-Api-Key` header on every
  authenticated request.
- Fallback: the server also accepts `Authorization: Bearer <token>`, because
  many client frameworks default to it. Same token, same secrecy — this only
  avoids a failed-guess round-trip. `X-Api-Key` remains canonical.
- Exception (bootstrap): `GET /` and `GET /skill.md` are public and need no
  token, so a fresh client can learn how to connect from the URL alone.
  They carry no secrets.
- Tokens are 256-bit random strings generated by the server at startup
  (or loaded from `--token-file`).
- The server MUST compare tokens in constant time.
- On missing/invalid token: `401` with the error envelope (Section 4).
- The token MUST NEVER appear in chat transcripts or URLs. It is entered
  via the platform's secure connection card and stored in the client's
  credential vault.

## 3. Endpoints

### 3.1 `GET /skill.md`

Returns the skill document (`text/markdown; charset=utf-8`) that teaches
a client how to use this bridge: tool semantics, approval discipline,
and usage examples. This is the same file as
`skills/muse-ai-local-bridge/SKILL.md` in the repo.

Purpose: zero-install client bootstrapping. The client fetches this
after obtaining the token and configures itself — no zip upload, no
manual skill installation.

### 3.2 `GET /api/tools/list`

Returns the list of tools available in the current server mode.

Response data:

```json
{
  "ok": true,
  "data": {
    "mode": "read-write",
    "project_roots": ["/home/user/projects/my-project"],
    "tools": [
      {
        "name": "read_file",
        "description": "Read a file inside an allowed root.",
        "parameters": {
          "path": "string (project-relative or absolute, MUST resolve inside an allowed root)"
        }
      }
    ]
  }
}
```

In `read-only` mode, write tools and `run_command` are omitted
from the list.

### 3.3 `GET /api/tools/call`

Invokes one tool. Query parameters:

- `tool` (string, required): tool name, MUST be on the list from
  `/api/tools/list`.
- `args` (string, required): URL-encoded JSON object of the tool's
  arguments.

Example:

```
GET /api/tools/call?tool=read_file&args=%7B%22path%22%3A%22README.md%22%7D
X-Api-Key: <token>
```

**Flat query parameters (compatibility).** Some client frameworks flatten
arguments into individual query parameters instead of the `args` JSON object:

```
GET /api/tools/call?tool=read_file&path=README.md&limit=50
```

The server merges these into `args`. String values are coerced to the scalar
type tools expect (`"true"`/`"false"` → boolean, numeric strings → number,
`"null"` → null). On a key conflict, the `args` JSON object wins. The `args`
JSON remains canonical — prefer it when you need precise types or nested
values.

## 4. Envelopes

Success:

```json
{ "ok": true, "data": { "...": "tool-specific payload" } }
```

Error (HTTP status 4xx/5xx):

```json
{ "ok": false, "error": { "code": "PATH_OUTSIDE_ROOT", "message": "human-readable" } }
```

Error codes (V1): `MISSING_TOKEN`, `INVALID_TOKEN`, `UNKNOWN_TOOL`,
`BAD_ARGS`, `PATH_OUTSIDE_ROOT`, `FILE_BLOCKED`, `WRITE_ATOMIC_FAILED`,
`COMMAND_NOT_ALLOWED`, `COMMAND_REJECTED_METACHAR`, `COMMAND_TIMEOUT`,
`MODE_READ_ONLY`, `INTERNAL_ERROR`.

## 5. Path rules (applies to every tool taking a path)

1. The path MUST resolve (after symlink resolution and `..`
   normalization) strictly inside one of the server's allowed roots.
   Anything else → `PATH_OUTSIDE_ROOT`.
2. The permanent blocklist is enforced even inside allowed roots:
   `.env` and variants (except `.env.example` / `.env.sample`),
   `*.key`, `*.pem`, `.ssh/`, `.aws/`, `.gnupg/`, `.npmrc`,
   `.git-credentials`, `credentials.json`, `*.token`, `.docker/config.json`,
   `.netrc`. Match → `FILE_BLOCKED`. (v3: extended list, see §11.)
3. `list_files` and `search_code` SHOULD respect `.gitignore` by default.
   `read_file` with an explicit path bypasses `.gitignore` (explicit
   path = owner intent) but never the blocklist.

## 6. V1 tool reference

Tool names are **frozen** as of V1 — clients depend on them.

### Read tools (all modes)

| Tool | Args | Notes |
|---|---|---|
| `list_projects` | — | Returns allowed roots (one entry in cwd mode, several in config mode). |
| `list_files` | `path` (dir, default root), `recursive` (bool, default true) | Respects `.gitignore`. |
| `read_file` | `path`, `offset` (0-based, optional), `limit` (optional) | Text files returned as UTF-8. Offset is **0-based** (v3 correction: the code was always 0-based; the doc wrongly said 1-based). |
| `search_code` | `pattern`, `path` (optional), `file_glob` (optional) | Literal match; respects `.gitignore`. |
| `git_status` | `project` (optional) | Per-file porcelain-style entries. |
| `git_diff` | `project` (optional), `staged` (bool) | Unified diff. |
| `git_log` | `project` (optional), `limit` (default 20) | |

### Write tools (`read-write` mode only)

| Tool | Args | Notes |
|---|---|---|
| `write_file` | `path`, `content` | Atomic (temp + rename). Size-capped (default 1 MB). Creates parent folders as needed. |
| `edit_file` | `path`, `old_text`, `new_text` | Exact match on `old_text`, written **literally** (no unicode-escape interpretation). One match required; zero or many matches is an error, never a silent partial write. Sequential application only. |
| `apply_patch` | `path`, `patch` (unified diff) | Atomic; applied with fuzz factor 0. |

### Command tool (`read-write` mode only)

`run_command`: `command` (string), `project` (optional), `timeout_s`
(optional, default 600).

Execution semantics (MUST):

1. The command string is checked for shell metacharacters **first**:
   `;`, `&&`, `||`, `|`, `$()`, backticks, `<`, `>`, `*` (outside the
   whitelisted pattern itself). Any hit → `COMMAND_REJECTED_METACHAR`,
   before pattern matching.
2. The remaining string MUST exactly match (or anchor-match) an entry
   in the server's allowlist. No prefix/substring matching.
   Non-matching → `COMMAND_NOT_ALLOWED`.
3. Execution is **without a shell**: argv array spawn, working directory
   locked to the target project root.
4. Default allowlist: `npm run build`, `npm run typecheck`, `git status`,
   `git diff`, `git log`. Extended at startup via `--allow` patterns.
5. On timeout → `COMMAND_TIMEOUT`; partial output is returned in `data`.

## 7. Approval model (honest statement)

Approval is enforced **client-side**: the AI client MUST obtain explicit
owner approval (showing the full command text / file path and diff)
before calling any write tool or `run_command`. The server trusts that
its caller did so. The threat model covers outsiders and mistakes, not
the owner attacking themselves. See `SECURITY.md`.

## 8. Audit

The server appends one line per write-tool call and per `run_command`
to `~/.muse-ai-local-bridge/audit.log`:
`timestamp, tool, path/command, result`. Append-only.

## 9. Versioning

- This spec is V1. Breaking changes require a spec version bump and a
  new `/api` path segment (e.g. `/api/v2/...`); V1 endpoints keep
  working.
- Additive changes (new tools, new optional args, new error codes) do
  not require a version bump.

## 10. V2 (fork, additive — V1 tools and endpoints are unchanged)

V2 keeps every V1 tool, endpoint and error code, and adds the tools below.
`/api/tools/list` now also returns `version: "0.3.0"`, `shell_enabled`
and `git_write_enabled`, so a client can tell at a glance what is on.

### 10.1 Persistent terminals (requires `--allow-shell`)

| Tool | Args | Notes |
|---|---|---|
| `terminal_create` | `project` (optional) | Spawns one `bash` in the project root. Returns `id` (`term-N`) + pid. |
| `terminal_list` | — | All live terminals: id, project, pid, running, buffered bytes. |
| `terminal_send` | `id`, `input` | Writes to the shell's stdin. Include a trailing `\n` to run it. |
| `terminal_read` | `id`, `offset` (default 0) | Buffered stdout+stderr from `offset`; returns new `offset`, `running`, `exit_code`. Buffer is capped at 512 KB (oldest output drops). |
| `terminal_kill` | `id` | SIGTERM + remove from the list. |

Terminals are per-project, cwd-locked to the root, and every
`terminal_create` / `terminal_send` / `terminal_kill` is audit-logged.
There is no idle auto-kill in v2 — kill terminals you no longer need.

### 10.2 Async exec jobs (requires `--allow-shell`)

| Tool | Args | Notes |
|---|---|---|
| `exec_start` | `command`, `project`, `timeout_s` (1–1800, default 600) | Runs via `bash -c` when shell is on; returns `job_id`. Output capped at 512 KB. |
| `exec_poll` | `job_id` | `{status: running\|done\|timeout\|killed, exit_code, output}`. |
| `exec_kill` | `job_id` | SIGKILL. |

Use this for builds/tests that outlive one HTTP call. `run_command`
(V1, allowlist, synchronous) is unchanged.

### 10.3 Full shell — opt-in, default OFF

`--allow-shell` (also `MUSE_BRIDGE_ALLOW_SHELL=1` or
`{"allow_shell": true}` in `~/.muse-ai-local-bridge/config.json`)
enables §10.1–10.2. Without it those tools are not listed and calls
fail with `SHELL_NOT_ENABLED` (403). `--read-only` overrides the flag:
in read-only mode no shell tool exists at all.

**Trade-off, stated plainly:** a shell in the project root can read
anything in that root — including `.env` files the V1 file tools refuse
to serve — and can run any command. That is the whole point of the
feature and also its risk. Only enable it behind a private tunnel
(Tailscale / named Cloudflare tunnel), never a public quick-tunnel URL,
and rotate the token if it may have leaked. See `SECURITY.md` §V2.

### 10.4 Full git (write side requires `--allow-git-write`)

| Tool | Args | Notes |
|---|---|---|
| `git_branch` | `project` | Read tool, always available. Lists branches + current branch. |
| `git_commit` | `message` (≤500 chars), `all` (bool), `files` (array) | `all:true` enumerates stageable files (`git ls-files`, tracked + untracked respecting `.gitignore`), filters each through the same Gate blocklist as `files`, then runs `git add -- <filtered>` (v3, RC2 — never a raw `git add -A`); `files` stages exactly those paths (each resolved in-root, blocklist-checked). |
| `git_push` | `remote` (default `origin`), `branch` | Remote/branch names are validated (`[A-Za-z0-9._/-]+`); argv spawn, no shell. |
| `git_checkout` | `branch`, `create` (bool) | `create:true` = `checkout -b`. |

Without `--allow-git-write` (also `MUSE_BRIDGE_ALLOW_GIT_WRITE=1` or
`{"allow_git_write": true}` in config.json) the three write tools are
not listed and fail with `GIT_WRITE_NOT_ALLOWED` (403). Read git tools
(`git_status`/`git_diff`/`git_log`/`git_branch`) are unaffected.

### 10.5 Stronger search + local skills (read tools, always on)

| Tool | Args | Notes |
|---|---|---|
| `glob_files` | `pattern` (e.g. `**/*.md`), `path`, `max_results` | Glob with `**`/`*`/`?`; respects `.gitignore` + blocklist. |
| `grep_code` | `pattern` (regex), `path`, `file_glob`, `context_lines`, `case_insensitive` | Regex search; invalid regex → `BAD_ARGS`. |
| `list_skills` | `project` | Skills found in `skills/`, `.agents/skills/`, `.opencode/skills/` under the root: `{name, path, description, source}`. Description comes from frontmatter `description:` or the first paragraph. |
| `read_skill` | `name` (or `path`) | Returns the skill's `SKILL.md` content (1 MB cap). Name must match a skill from `list_skills`. |

### 10.6 MCP mode (`--mcp`, stdio JSON-RPC)

`node server.js --mcp [--allow-shell] [--allow-git-write] [--read-only]`
runs a stdio MCP server instead of the HTTP API: no port is opened,
nothing but JSON-RPC goes to stdout (logs go to stderr). Supported
methods: `initialize` (protocol `2024-11-05`), `ping`,
`tools/list`, `tools/call`, `notifications/*` (ignored). `tools/list`
exposes exactly the tools the current flags allow; `tools/call`
dispatches through the same code as the HTTP API, so root scope,
blocklist, read-only and shell/git-write gates all still apply.
Stdio is the trust boundary here — no token is checked over stdio,
because only a local process that launched the server can speak to it.

Example (OpenCode `opencode.json`):
```json
{ "mcp": { "muse-bridge": { "type": "local", "command": ["node", "/path/to/muse-ai-local-bridge/server.js", "--mcp", "--allow-shell"], "enabled": true } } }
```

### 10.7 New error codes (V2)

`SHELL_NOT_ENABLED`, `GIT_WRITE_NOT_ALLOWED`, `TERMINAL_CLOSED`.
All other V1 codes are unchanged.

## 11. V3 (fork, additive — V1/V2 tools and endpoints are unchanged)

`/api/tools/list` now returns `version: "0.3.0"`. Tool names, response
shapes and error envelopes are unchanged. What changed is under the hood:

- **Central Gate (`lib/gate.js`, fail-closed).** One module validates
  every git ref/argv (`validateRef` rejects leading `-`, `validateArgv`
  inserts `--` before positional args and rejects user flags), every
  path list (blocklist + root scope), every regex (max 200 chars, nested
  quantifiers rejected) and every file size (1 MB, checked *before* any
  read). If the Gate is disabled, all write/shell/git tools refuse with
  `GATE_DISABLED` — there is no path that runs without it.
- **Bounded processes (`lib/process-manager.js`).** Max 8 terminals /
  16 jobs (env `MUSE_BRIDGE_MAX_TERMINALS` / `MUSE_BRIDGE_MAX_JOBS`);
  finished ones are evicted LRU, idle terminals are killed after
  30 min, finished jobs are dropped after 10 min; a full manager
  refuses with `RESOURCE_EXHAUSTED` instead of forking more. Kills are
  process-group kills (`detached:true` + `kill(-pid, SIGKILL)`), so no
  orphaned grandchildren survive `terminal_kill` / `exec_kill` / timeout.
- **Git, 1 spawn per call (`lib/git-service.js`).** `git_status` is a
  single `git status --porcelain=v1 -b`; `git_branch` is a single
  `git branch` plus the current branch read from `.git/HEAD` (cached
  1 s, invalidated by mtime). `git_push` / `git_checkout` refs go
  through the Gate (RC1).
- **Search in a worker thread (`lib/search.js`).** `grep_code` /
  `search_code` (directory mode) match inside a `worker_threads`
  worker with a 2 s timeout — a ReDoS pattern returns `TIMEOUT`
  instead of hanging the server; a dead worker is a rejected call,
  never a hang.
- **Audit log (`lib/audit.js`).** Rotates at 10 MB (keep 3), fails loud
  (write failure → stderr + degraded flag, never a silent `catch {}`),
  and never logs terminal input (only the terminal id + byte count).
- **Token.** Printed to stderr only at startup, never to stdout (stdout
  is the MCP channel and must never carry a secret).
- **`read_file` offset is 0-based** (§6, corrected to match the code —
  the code itself did not change, so old clients are unaffected).
- **New error codes (V3):** `GATE_DISABLED` (503), `RESOURCE_EXHAUSTED`
  (429), `TIMEOUT` (408). All V1/V2 codes are unchanged.

### 11.1 Explicitly deferred (not in v3)

PTY support, sandboxing (`bwrap`) and streaming (SSE/NDJSON) are
**DEFERRED** — see README "V3 — deferred (P2)" for the reasons. They
need an optional native dependency / Linux-only tooling / a new
transport, and none of them may break the zero-dependency default.
